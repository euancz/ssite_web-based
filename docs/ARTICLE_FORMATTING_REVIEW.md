# Article formatting: implementation and migration review

Prepared October 27, 2026. After review and the user's instruction to continue, the scoped migration was applied successfully. Article formatting is enabled.

## Author experience

Articles offer Plain text and Formatted text (Markdown). The editor remains a normal textarea with Bold, Italic, Heading, List, Quote, and Link controls; it is a Markdown source editor, not a visual WYSIWYG editor. Authors can type formatting without JavaScript. Plain text retains the existing live preview. Formatted text offers an explicit Refresh preview action so unsaved text is sent to the authenticated server only when requested. Edits invalidate the previous formatted preview and abort pending responses.

Drafts preserve the selected format through resume and submission. Existing article content is not converted. New articles default to plain text; authors explicitly opt into Markdown. Omitting format on an update preserves the stored value. Changing format or content follows the current review-reset workflow.

The existing 300-word limit continues to count source whitespace-separated words, including Markdown markers. Article content also has a 20,000-character ceiling matching drafts and preview requests; this bounds parser workload, including pathological single-word input. Existing database content is not truncated or rewritten by the migration.

## Rendering and security

`ArticleContent` uses the already installed League CommonMark parser with raw HTML escaped, unsafe links disabled, and finite nesting/delimiter limits. Custom renderers allow only absolute HTTP(S) links and render inline image descriptions without loading their URLs. Uploaded article images continue through the existing validated upload path. No new dependencies or frontend framework were added.

Formatted detail pages and server previews use the same renderer. Plain articles keep escaped rendering. List, Discover, and search excerpts convert formatted content to plain text and escape it for their output context. Searches still match stored source text; JSON response keys are unchanged.

The new POST `workspace.articles.preview` endpoint requires authentication, profile completion, article-create permission, CSRF protection, and the existing content-write throttle. It validates format and character length, returns private/no-store JSON, and writes no articles, drafts, or notifications. Only its restricted server-generated HTML is inserted into the preview; user-entered HTML is never inserted directly.

## Approved migration

Only `articles` gains `content_format VARCHAR(16) NOT NULL DEFAULT 'plain'`. No index or relationship is required. No existing column, file, ownership, status, timestamp, or text value is modified. The format discriminator is necessary to avoid interpreting Markdown-like characters in legacy plain-text articles.

Migration: `database/migrations/2026_10_27_000004_add_content_format_to_articles_table.php`.

Pre-migration read-only MySQL inspection confirmed that the column and ledger entry were absent and the feature availability check was false. Laravel pretend mode generated this SQL for review:

```sql
alter table `articles` add `content_format` varchar(16) not null default 'plain';
```

After approval, only this command was executed:

```powershell
php artisan migrate --path=database/migrations/2026_10_27_000004_add_content_format_to_articles_table.php --force
```

Before execution, capture article count and a checksum of all existing values. Afterward, verify unchanged data, the column/default, ledger entry, and all existing formats set to plain. Do not run legacy pending migrations. ALTER may lock the table and MySQL DDL is not generally transactional; inspect before retrying interrupted execution. Dropping the format column would lose rendering intent and requires separate approval.

Until migration, the format controls are hidden, ordinary article/draft writes ignore submitted format, and the preview endpoint returns 404 after authorization. The existing article UI continues to work.

## Validation

- Full isolated suite: **78 tests, 1,220 assertions passed**. Six new tests cover legacy rendering, migration defaults, raw-HTML/link/image safety, preview permissions and bounds, no persistence, draft round-trip, explicit/omitted formats, word limits, readable excerpts, and public/private boundaries.
- Production build and Blade compilation/cache clear passed. JavaScript syntax, PHP formatting, and whitespace checks passed.
- Chrome checked editor and formatted article fixtures at 1440px, 768px, and 320px with no page overflow or JavaScript exceptions. Bold insertion, safe preview display, and no-JavaScript controls passed. Browser preview responses were generated by the real renderer and served as fixture JSON; actual endpoint authorization and validation were exercised by Laravel tests.
- An initial full-suite attempt collided with a simultaneous Blade cache operation on Windows. Running the suite without cache mutations passed. Keep Blade compilation/cache clearing sequential with tests and fixture rendering.

This adds formatted articles only. Other modules keep plain text. Durable draft attachments, scheduling, immutable history, and richer analytics remain separate work.

Only `2026_10_27_000004_add_content_format_to_articles_table` ran. Read-only verification confirmed `varchar(16) NOT NULL DEFAULT 'plain'`, the migration-ledger entry, and feature availability. Article count remained 1 and the SHA-256 checksum of all pre-existing article values matched before and after execution. The existing article is plain text; no content was converted. No legacy pending migrations were executed.
