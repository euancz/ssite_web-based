## Capability matrix to confirm

### Officer positions

| Position | Post modules | Submission state | Review | Manage existing content | View non-public content | Single holder by default |
| --- | --- | --- | --- | --- | --- | --- |
| President | Articles, Activities, Achievements, Documents, Liquidation | Approved when `president_posts_auto_approved=true`; reviewed by self with timestamp | Approve/reject all pending items | Edit/archive/restore/bulk archive any item; permanent delete by default | All modules | Yes |
| Secretary | Documents | Pending | No | Own items in allowed module only | Own non-public items only | No |
| Auditor | Liquidation | Pending (proposed yes) | No | Own items in allowed module only | Own non-public items only | No |
| Multimedia | Articles, Achievements, Activities | Pending | No | Own items only (proposed) | Own non-public items only | No; several holders |
| Other / missing / unrecognized | None | Cannot submit | No | None | Same as student | N/A |

`officer_position` grants capabilities only while `role=officer`. Position matching is trimmed and case-insensitive against config keys; only canonical config titles are assignable and stored. Unrecognized legacy strings remain stored until explicitly reassigned and grant no capability.

### Roles

| Role | Assign roles | Content capabilities | About roster | Non-public items | Dashboard / landing |
| --- | --- | --- | --- | --- | --- |
| Guest/student | None | No writing/review; public content as configured; Liquidation remains login-only | None | No | Home |
| Officer | None | Position matrix above | None | President: any; other poster: own only | Officer dashboard if position has capabilities, otherwise home |
| Adviser | Student to officer and officer to student, including position assignment; cannot target self or protected accounts | None | No | No; private records 404 | Adviser role-assignment dashboard |
| Superadmin | Student/officer to adviser and adviser to student; no officer assignment or superadmin assignment | None | No | No; private records 404 | Superadmin adviser-assignment dashboard |

The user confirmed that adviser and superadmin duties are limited to role assignment. Neither role manages the About roster; its routes remain present for URL compatibility and are denied by `can:manage-officers`.

## Approved answers and defaults

The user approved the defaults below and confirmed that adviser and superadmin duties stop at role assignment.

1. Position titles / Multimedia: retain the current roster display ordering where possible; use canonical assignable titles `President`, `Secretary`, `Auditor`, `Multimedia`. One `Multimedia` position permits multiple holders. Existing `Multimedia (Creative)` and `Multimedia (Documentation)` are display/history labels and are not assignable unless you request a mapping.
2. Auditor submissions: pending President review (**yes**).
3. Vice President, Treasurer, PRO and all other positions: view-only until explicitly assigned capabilities (**yes**).
4. President permanent delete: **yes**, with existing confirmation and file cleanup rules.
5. Single President: **yes**, controlled by `single_holder_positions`; reject a second assignment with a clear validation message until reassignment.
6. No-President fallback approver: **none**; submissions stay pending, no review notification is sent, adviser dashboard warns (**yes**).
7. About roster managers: **adviser no, superadmin no** (confirmed; role assignment is their only management duty).
8. Multimedia officers edit one another's posts: **no**, own posts only.
9. Adviser/superadmin pending counts: **yes**, count-only; adviser warning if no President. Superadmin count visibility is not explicitly repeated in its dashboard requirements; proposed count-only visibility, no titles/content.
10. Legacy adviser/superadmin-authored posts: preserve data; only President can manage them (**yes**). They do not become publicly hidden if already approved and active.

## Config proposal

Keep `officer_positions` as the ordered About/history display list. Add `positions` keyed by assignable canonical labels, each with `modules`, `can_review`, `auto_approved`, and `single_holder`; add `single_holder_positions` as the centralized enforcement/config list. Proposed shape:

```php
'positions' => [
    'President' => ['modules' => ['articles', 'activities', 'achievements', 'documents', 'liquidations'], 'can_review' => true, 'auto_approved' => (bool) env('SCHOOL_PRESIDENT_POSTS_AUTO_APPROVED', true), 'single_holder' => true],
    'Secretary' => ['modules' => ['documents'], 'can_review' => false, 'auto_approved' => false, 'single_holder' => false],
    'Auditor' => ['modules' => ['liquidations'], 'can_review' => false, 'auto_approved' => false, 'single_holder' => false],
    'Multimedia' => ['modules' => ['articles', 'achievements', 'activities'], 'can_review' => false, 'auto_approved' => false, 'single_holder' => false],
],
'single_holder_positions' => ['President'],
'president_posts_auto_approved' => (bool) env('SCHOOL_PRESIDENT_POSTS_AUTO_APPROVED', true),
```

To avoid two configuration sources for auto-approval, implementation should use `president_posts_auto_approved` as the setting and position metadata should declare whether it can auto-approve (the President only); the setting determines the runtime toggle. Remove `adviser_posts_auto_approved` and all readers. Remove `notify_superadmin_of_reviews` if present (it was not found in the searched source).

### Data impact (counts not available)

No row-level identifiers or counts can responsibly be reported without the requested read-only aggregate. The following populations will lose current abilities under the proposed matrix:

- Every officer currently has `canPost()` for every module; only configured President/Secretary/Auditor/Multimedia capabilities will remain. Other positions, null positions and unrecognized strings become view-only.
- Advisers and superadmins currently have broad post, review, bulk archive, and manager rights; they lose all content operations. Superadmins also lose officer/position assignment.
- Existing adviser/superadmin-authored records remain unchanged in storage and public state. Their owners lose private access and content controls; President can manage all such records.
- Existing position list contains labels including Vice Presidents, Treasurer, Public Information Officer, Business Manager, Social Media Manager, two Multimedia sub-roles, and IT Representatives. Unless mapped by explicit confirmation, those roles are view-only; this is a data cleanup decision for the user, not an automatic rewrite.

## User methods, policies, Gates, and validation

- `User::position()` returns null unless role is officer; otherwise trim/case-fold match to config key and return that canonical key. `isPresident()` is based on the canonical position. `canPostIn(string $module)` and `postableModules()` read config. `canReview()` is President-only. `canAssignOfficers()` is adviser-only; `canAssignAdvisers()` is superadmin-only. Keep `isAdviser()` / `isSuperadmin()` as identity helpers, not general content authorization.
- Each content policy uses `canPostIn(module)` for create, President or owner plus continuing `canPostIn(module)` for update/archive/restore, `canReview()` for approve/reject, President-only delete by default, and President or owner for non-public view. Ownership compares `created_by_user_id` with `user_id` only. Adviser/superadmin must not be included in private-item exceptions.
- Gates: `manage-officers` denies both adviser and superadmin; `manage-advisers` allows superadmin; `manage-users` opens only the relevant role-assignment manager; `view-post-dashboard` derives from `postableModules`; `review-posts` derives from `canReview`.
- User assignment policy rejects self, superadmin target, and adviser target for adviser actor; adviser may assign `student|officer`, superadmin may assign `student|adviser`. Require canonical configured position only for officer; set null otherwise. Enforce one President when configured. Role/position fields remain outside fillable and are assigned explicitly from validated values. Put role update, current-year officer-term synchronization, and optional role_changes insert in one transaction. Current-year removal must never delete prior history.
- Role assignment routes should expose a policy `can:changeRole,user` middleware. Roster routes use the confirmed `can:manage-officers` ability. Controller authorization remains defense in depth.

## Notification rules

| Event | Recipient rule |
| --- | --- |
| Pending submission or resubmission | All users where `canReview()`; with one-President setting this is the President. If none, nobody; adviser dashboard warns. |
| Approve/reject | Author if account still exists; rejection includes reason. Action is conditional on pending state so double submission cannot duplicate notices. |
| Published broadcast | Everyone except author and actor, after President approval or President direct post. |
| Archive/restore/delete | No notification. |

Review notices never go to advisers or superadmins; published notices never duplicate the author approval notice. Reviewer recipients are resolved at action time so reassignment transfers future notices to the new President.

## Tabs, menus, dashboards, and manager behavior

- Capable non-President officer in an allowed module: Published, My Posts, Archived (own). President in all modules: Published, Pending Review + count, More (Rejected, Archived, All). Everyone else and unsupported modules: Published only. Invalid `tab` falls back to Published.
- Composer, New, edit/archive/restore, approval/rejection, bulk archive, and permanent delete controls render only through abilities in Blade. President can manage any item; non-President can manage own items only while their position still allows that module. Two Multimedia officers do not share ownership.
- Manage menu: President Dashboard + Review Posts count; Secretary/Auditor/Multimedia Dashboard; adviser Manage Users; superadmin Manage Advisers + Role history if present. Show Officer position beneath identity. Preserve the shared nav pill.
- President dashboard: per-module pending counts and needs-attention list. Posting officer dashboards: own module posts by status with rejection reason. Adviser dashboard: role assignment entry point, pending counts only, and no-President warning. Superadmin dashboard: adviser assignment list and role history; pending counts only if shown. Neither role can manage the About roster or see private post titles/content.
- Adviser manager: student/officer rows only editable; role select limited to student/officer, canonical position dropdown only for officer; no controls for self/adviser/superadmin; unknown position warning. Superadmin manager: assign/revoke adviser only; never officer assignment or superadmin role assignment.
- Login destination: officers with configured posting capability to officer dashboard; unsupported officers and students to home; adviser to user/manager dashboard; superadmin to adviser manager. Preserve intended route only if authorized.

## Risks and build order

1. No President means pending submissions accumulate without review notifications; adviser sees counts and a warning but cannot open or review them. Operational mitigation is to assign a President before relying on submissions.
2. Existing position strings may not map to canonical assignable titles. They become view-only until the adviser deliberately reassigns them; no automatic data rewriting.
3. The single-holder constraint must be transaction-safe against two concurrent assignments; use a locking query or equivalent database-safe check. Schema changes are prohibited.
4. Adviser and superadmin pending-count visibility: yes, count-only (confirmed default).
5. Existing no-op migration requirement applies only if code absolutely requires a migration file; no schema change is planned and no migration/seeder will run.
